# Solaris 1.0 "Pauline" RC5

RC5 is RC4 plus Windows fixes and two startup fixes on every platform;
nothing else changed. In RC4, singleplayer on Windows stopped at "Server exited
during startup", and a Windows-hosted server failed the same way.

## Changes

- Windows: the server starts. RC4 locked the world by opening the world
  directory as a file. Windows refuses that with "Access is denied (os error 5)".
  On Windows the lock is now the file `.solaris-world.lock` inside the world
  directory; Linux and macOS lock the directory as before.
- Windows: loot tables and datapacks found by walking a directory get resource
  names with `/`, and backup manifests list files with `/`. RC4 used the system
  path separator, and on Windows the server stopped at startup with
  `invalid identifier: "minecraft:chests\abandoned_mineshaft"`.
- Windows: plugin packages load. RC4 could not read a package's optional
  `config.toml` on Windows and refused every package. A `config.toml` must be
  a regular file; links are refused.
- Windows: operator, ban, mute and whitelist changes are saved
  (`ops.json`, `banned-players.json`, `banned-ips.json`, `muted-players.json`,
  `whitelist.json` and the whitelist on/off setting). RC4 failed there with the
  same error as the world lock.
- All platforms: a new world whose first start is stopped before it finishes
  opens on the next start. RC4 created the world's database first and wrote the
  first save later; a start stopped in between (for example by the client's
  three-minute start limit on a slow or busy PC) left a world that failed with
  `native global/checkpoint: missing` from then on. RC5 marks a new world with
  the file `.solaris-first-start` in its world directory until the first save
  is written. A start that finds the marker runs the first start again, or
  opens the world normally if its first save was already written. A world
  already left in that state by RC4 has no marker and still fails the same way.
- All platforms: a server starting on a world that another server still holds
  waits up to 30 seconds for it to exit, then refuses with `world ... is
  already leased` as before; RC4 refused at once. In testing, a singleplayer
  client stopped together with its server (one signal to both) and started
  again right away hit this once, while the previous server was still saving
  the world. Offline world commands still refuse at once.

## Upgrade

Replace the binary. RC4 worlds, configs and content caches work unchanged. For
older versions, follow the [RC4 notes](https://github.com/kaiserproger/solaris/releases/tag/v1.0.0-rc.4).
Before the first start of a new install, download the content cache:
`solaris content import --version 26.3 --download`.

## Validation and known limitations

Core: full L2 correctness (fmt, strict clippy, code-health, 6,964 tests)
passed on the release Rust sources.

Linux: an independent breaker attacked the client package built from these
sources the way the release workflow builds it.

- A new world's first start was killed at each step (marker written, database
  being created, database created, start area generating, server listening),
  three times each; every world opened on the next start and a native client
  joined it. RC4 killed while generating the start area fails with
  `native global/checkpoint: missing` on the next start. A database without a
  checkpoint and without the marker is still refused.
- With the previous server kept holding the world, Play from a relaunched
  client waited and then entered the world once that server exited (3 of 3).
  With the world held for longer than 30 seconds, the start was refused, and
  Play again in the same client after the old server exited entered the world
  (3 of 3). Relaunch and Play right after the client was killed in the world
  (3 of 3), and right after a stop that signalled client and server together
  (3 of 3), entered the world.
- A clean install through the launcher's window downloaded content and
  entered a new singleplayer world; a clean install with the launcher running
  headless did the same; an RC4 world with a placed block, a chest item and a
  settlement opened in RC5 with all three; title-screen connect and rejoin
  held. Each of these ran once.

Windows: tested in a Windows 11 VM with the RC4 client package, its
`solaris-v2.exe` replaced by local release builds of these sources (the
release package is built by CI). With a build from before the lease change, a
new Survival world was created and entered; a second new world's first start
was stopped after its database appeared, the client showed "Server exited
during startup", Play started the world again and the player entered it; and
operator and whitelist changes made there were saved to `ops.json` and
`whitelist.json`. With the final build, a second server started on a world in
use waited and was listening once the first was killed, and a world whose
server had been killed during play opened again and the player entered it.
The Windows release package was not tested before tagging.

macOS: on a GitHub-hosted macOS 15 (Apple silicon) runner, the core tests for
the two startup changes passed on the release Rust sources: a new world whose
first start stopped before its first save, or before its database existed,
opens on the next start; a database without a checkpoint and without the
marker is refused; a start waits for a world another holder still has. No
client and no macOS release package were run on macOS before tagging.

The client gives a new singleplayer server three minutes to start. On a slow or
busy machine the first start of a new world can take longer; the client then
stops the server, and the next Play runs the first start again.

Still unsupported on Windows, each failing with an error: offline `backup` and
`restore`, the console `/backup` command, and `world import-anvil`,
`export-anvil` and `census`.

All other RC4 notes and known limitations still apply.
